# 历史补洞与连续测试网观察

本阶段把外部执行从有界手工回报接收推进到“持久历史游标 + 原子补查 + 可重连的只读观察节点”。策略自动下单仍未接入；账户币种余额不是策略收益。目标仓位、信号/仓位/过滤组合和持久 TWAP 按此基础继续推进。

## 为什么不能把最后收到的推送 ID 当成完整高水位

私有回报没有可用于本账户全部活动的连续全局序号。收到较大的 trade ID 不证明较小的成交都收到，ID 也可以合法跳号。因此分别维护每个已注册 symbol 的 REST order/trade 游标；WebSocket 接收不会推进它们。

`ledger-init` 在无外部活动、无挂单的专用测试账户上连续取得两次身份、完整余额、历史头部；相同才把 UID 派生身份、工具、期初资产与种子游标一次提交。基线之前的历史属于期初资产，不能再次记账。旧版已绑定账本没有可验证的种子来源，继续走原逐单对账；不会静默追加当前游标。

官方协议来源固定到 [Binance Testnet REST b45e91d](https://github.com/binance/binance-spot-api-docs/blob/b45e91d9824b6d523e8c9656de4efd1083c261e7/testnet/rest-api.md) 的 `allOrders` / `myTrades`：使用 inclusive orderId/fromId、最多1000条/页。这里重叠最后一个已确认条目以核对重复经济内容；初次跳过种子。

每轮先收集、再提交：

1. 验证检查点、账户身份与历史未回退/重置。
2. 按订单、成交分页，检查 symbol、严格递增、数量上限与历史头部覆盖；整页满时必须继续查询下一页，不能猜测已完成。缺少历史证据的未知/待完成意图按原 client ID / 稳定 orderId 查询。
3. 查询全账户挂单与完整余额；外来已关闭订单也会在已注册 symbol 的新历史内阻断。
4. 一个 SQLite WAL/FULL 事务写入订单、去重成交、原币资产变化、账户观测、确认游标、轮次统计与校验和。审计全部订单/成交和全部币种变化，一项冲突则全部候选回滚。

默认每页200、每轮最多256个订单/成交页面、最多100000条记录；每种统计/持久表有原有容量上限，恢复轮次最多100000。失败保持需要核对，不能提交最大已见 ID。检查点覆盖绑定身份、工具、期初资产、种子/确认游标和轮次；SHA-256检测意外损坏，不是认证签名，不能抵御能同时篡改内容和摘要的人。

REST采集不是交易所原子快照；Ready代表本轮已取得并核对的证据，不能证明最后一个请求之后没有新活动。先订阅与周期补查缩短观察窗口，但没有全局事件序号；账户应隔离其他交易来源。

历史完备性依赖交易所分页和保留期限；短页/空页被当成该端点完成前缀。只覆盖注册的 symbol；全账户余额/挂单核对不能证明其他 symbol 的外部净零活动不存在，也不会重新验证每一个旧终态订单的服务器内容。交易所重置、保留缺失、外部资金变化须人工分类，不能自动吸收或补余额。

## 连续观察的所有权与状态

网络线程独占已认证私有连接；主线程独占 SQLite。256条有界队列、wire frame/message 64KiB、解码执行事件64KiB校验；容量约束不能当成整个进程16MiB RSS保证。队列满或消费年龄超过5秒结束代次并补查，不静默丢帧继续交易。

每次本地代次持久化 `connecting → recovering → ready → gap/stopped`；最多10000代次。先订阅并缓冲，再 REST 补查，再处理回报。旧代次不可向新代次写入。进程重启把未关闭连接标记 gap；新进程始终重新认证/REST，不能续用 Ready。

正常无成交可以没有私有账户事件。60秒检测的是线路消息/服务器 ping/pong 静默，不是成交回报静默。读取2秒、写入5秒、认证等待12秒；DNS/场所请求也有各自边界，CLI实际时长可能超过目标观察秒数。协议/身份/容量格式冲突与线程panic失败关闭；传输、服务器终止、队列满及过期帧可重连，累计最多8次，退避1..30秒。REST或入账失败停止本次节点，不能被自动分类成可以交易的恢复成功。

每30秒额外 REST 补查。退出先停止并 join 网络线程，保留真实错误，再用 REST 覆盖未消费队列尾部。主动停止也保留需要新订阅/核对；最终资产审计完成不意味着连接仍 Ready。它是**只读持续测试网观察**，没有自动下单/撤单、主网、策略生命周期或生产 SLA。

```sh
cargo build --locked --release --features network --bin kaze-testnet
# 新的专用数据库；使用已有本机测试网凭据，不要提交凭据。
target/release/kaze-testnet reports/new-history.db ledger-init BTCUSDT
target/release/kaze-testnet reports/new-history.db monitor 120
# 只读故障验收：第一次消费者3秒后主动终止，真实连接释放并自动重连。
target/release/kaze-testnet reports/new-history.db monitor-gap 90
# 故障验收会发出一笔虚拟买单，失败只查原意图，不重发。
python3 scripts/history_acceptance.py --binary target/release/kaze-testnet --directory reports/new-history-pilot
cargo run --locked --release --example history_recovery_bench
```

## 证据与解释范围

[真实漏收成交汇总](evidence/v08/testnet-gap-summary.json)保留一笔虚拟订单、应用成功 ACK 抑制、原订阅 receive 次数为0、主动客户端关闭、重订阅后实际成交补回、原币费用/所有资产变化、重复意图0新增POST及独立进程一致性。成交可能发生在主动关闭之前；没有物理断包或“成交发生在断线后”的时间证明。原始账户/UID和凭据仅保留在本机忽略的 reports/configs。

[只读持续观察](evidence/v08/testnet-monitor-summary.json)记录实际时长、代次、事件、周期核对次数和0POST；有界运行不代表24h、真实部分成交或全部网络故障验收。

[完整本地恢复对照](evidence/v08/history-recovery-bench.json)以同一当前二进制中的旧逐单算法与新游标算法、同一期初/终态历史、同一完整订单/成交/原币资产审计，每组7轮交替运行。模拟场所采用有序索引，计时外预装合成历史；计时包括本地证据处理、SQL WAL/FULL和最终审计，排除真实网络/签名/服务器时钟请求。每轮完整经济投影完全相同；新路径还提供更强的整轮失败原子性，因此不是两套故障行为完全相同的系统。

一币对2000终态订单/成交时，旧算法每轮4004次数据 REST 操作，新算法7次。适配器签名请求还会额外GET服务器时间，调用数不包含这些时钟GET。未测真实往返时间、逐事件延迟分位数或vn.py/ABU/Nautilus/Barter同场所完整路径，不能用请求数推导线上提速倍数。重放账务查询补全 `observation IS NOT NULL` 后实际使用 `venue_order_identity` 部分索引；查询计划见[SQL证据](evidence/v08/sql-query-plan.json)。旧算法与新算法共享这个修复，性能对照没有把独立SQL修复只分给新路径。

旧v05 24h观察已因行情过期失败，约10056秒、1210292条报价，独立恢复状态/链一致，见[运行](evidence/v08/live-paper-v05-failed.json)、[验证](evidence/v08/live-paper-v05-validation.json)。保留故障保护，没有放宽时效阈值凑足24h；旧版本失败和新版本有界观察均不构成全天通过。

本机最终七轮结果：200订单/成交中位旧路径23.024ms、新路径10.974ms（2.10×）；2000订单/成交49.491ms→21.976ms（2.25×），各轮经济投影一致。这是当前二进制内部的恢复算法比较，不能称为超过vn.py或Barter；原始轮次/硬件/二进制哈希保存在上述JSON。SQL规划修复之外的完整组件开销仍随历史规模增长，没有常数时间全审计承诺。

最终二进制只读重连观察91.642秒、2个新连接代次、1次主动消费者中断/自动重订阅、5轮REST核对（35次数据请求）、0新增POST，无私有执行事件。这证明该有界静默连接的ping处理/周期补查/重连路径，不是间隙新成交证明或全天运行。另一个漏收成交试验提供实际成交补回。两份记录与本地验证使用同一二进制哈希。整个阶段共3笔独立小额虚拟买入（前两次为中间构建），见[尝试记录](evidence/v08/pilot-attempts.json)。
